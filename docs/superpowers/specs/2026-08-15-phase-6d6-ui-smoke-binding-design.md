# Phase 6D.6 Development UI-Smoke Binding and Capture Design

**Date:** 2026-08-15  
**Owner:** EmuChef proper / Shared Runtime  
**Status:** Approved design; implementation not started  
**Phase impact:** Phase 6D remains **In progress**. Phase 6E remains **Planned**.

## 1. Problem

Phase 6D.6 already defines development UI smoke as mandatory closure evidence. Each of two composite repetitions must cover cancellation, transport loss, root revocation, low storage, and host sleep/runtime loss, and every subcase must bind the observed UI state to one exact passing physical backend run and trace.

The evidence schema and validator already encode that contract, but the repository does not yet provide a trusted product path that can take an accepted physical backend result, project it through the production Tauri execution/recovery presentation logic, render it in the normal React terminal execution UI, and capture the sanitized state required by the `ui_smoke_composite` evidence contract.

Without that binding/capture plumbing, the two UI-smoke repetitions cannot be collected truthfully even after the required physical records exist.

Manual and physical validation are explicitly deferred for this slice. The implementation must make later UI qualification possible without creating, synthesizing, or claiming any physical or UI-smoke evidence now.

## 2. Decision

Use an **evidence-bound terminal projection mode** available only in a deliberately gated development real-execution build.

The mode will accept only an existing, checked-in, contract-valid **passing** Phase 6D.6 physical evidence record from the repository-controlled evidence location. Trusted Rust/Tauri code will resolve and validate that record, confirm its exact backend run/trace/category binding, derive the corresponding terminal product state through the existing production execution/recovery projection path, and expose that state to the same React terminal execution presentation used for normal retained executions.

A qualification-only capture action will serialize only the already-sanitized UI state required by the Phase 6D.6 `uiSmokeRecord` contract, calculate its canonical digest, and bind it to the selected backend run/trace and current development-build identity. The operator observation and final composite evidence record remain manual evidence-collection responsibilities and are not generated by the application.

This design deliberately does **not** replay a physical failure through the GUI. Physical proof remains the responsibility of the accepted backend evidence record; UI smoke proves that the production presentation and recovery surface truthfully represents that independently proven backend terminal condition.

## 3. Why this design

### 3.1 Benefits

- Reuses the existing Phase 6D.6 evidence contract instead of creating a second fault-injection system inside the application.
- Preserves production Tauri and React projection code as the source of truth for authored issue, remediation, terminal accounting, partial-change presentation, authority invalidation, recovery state, and controls.
- Lets UI smoke bind to exact independently collected backend evidence rather than to a synthetic terminal fixture.
- Keeps destructive/root/storage/sleep transitions out of a new UI-specific harness.
- Keeps normal simulation, normal real-development execution, packaging, and production behavior unchanged unless every qualification gate is present.
- Allows deterministic automated testing of the bridge and capture path without claiming that automated tests are physical or UI evidence.

### 3.2 Rejected alternatives

**Directly perform each physical interruption from the Tauri UI.** Rejected because it would duplicate the Phase 6D.6 physical harness, add another destructive qualification surface, and conflate backend physical proof with frontend presentation proof.

**Static frontend fixtures generated from `scenario-manifest.json`.** Rejected as the qualification authority because a static fixture cannot prove binding to an actual passing physical backend run and trace. Static fixture-style construction remains acceptable only as supporting automated test input around the trusted bridge.

## 4. Security and authority boundaries

### 4.1 Qualification gates

The UI-smoke mode must be unavailable unless all of the following are true:

1. debug build;
2. Cargo `real-execution` feature compiled;
3. existing global real-ADB qualification opt-in is present; and
4. a new exact Phase 6D.6 UI-smoke opt-in is present.

The new opt-in must not be enabled by ordinary `tauri:dev:real`, production packaging, release scripts, CI application launches, or default environment configuration.

### 4.2 Evidence source authority

Trusted Rust/Tauri code owns evidence discovery and reading. React must not provide:

- an arbitrary filesystem path;
- raw physical record JSON;
- a trace payload;
- a backend issue code;
- a scenario category; or
- a development-build digest.

The bridge resolves only files underneath the fixed checked-in Phase 6D.6 evidence location. It must reject symlink/path escapes and unsupported file types.

The caller may select only a safe opaque/enum-like candidate identity projected by trusted code, such as repetition/category plus a sanitized display label. Exact path resolution stays native.

### 4.3 Accepted backend evidence

A record is eligible only when all existing Phase 6D.6 validation rules required for a passing physical record succeed. The bridge must additionally require:

- `outcome == passed`;
- exact physical `runId` and `traceDigest` identity;
- scenario category compatible with the requested UI-smoke subcase;
- observed issue compatible with the authoritative `uiSmokeContracts` entry;
- no duplicate or ambiguous candidate selection; and
- an evidence commit/build provenance that is representable by the existing contract.

Failed, blocked, skipped, malformed, stale, category-mismatched, issue-mismatched, duplicate, or missing records never become UI qualification input.

The implementation should reuse or share validator/domain logic rather than create a weaker Tauri-only interpretation of the evidence contract. Node remains the final repository-level manifest validator, but the trusted application bridge must fail closed independently before projection.

## 5. Projection architecture

### 5.1 Core rule

The UI-smoke bridge must not maintain its own catalog of user-facing titles, issue text, remediation, partial-change wording, recovery state, or control policy.

The selected physical terminal condition is converted into the same internal terminal/report representation consumed by the existing production Tauri projection code. The existing projection code then produces the sanitized execution/recovery DTO consumed by React.

If existing projection code cannot be called without a live sidecar execution handle, refactor the minimum pure projection logic into a shared internal function used by both:

- the normal retained-execution path; and
- the development UI-smoke evidence bridge.

Do not create a parallel projection implementation merely to avoid a small refactor.

### 5.2 No execution ownership

Loading a UI-smoke terminal projection does not:

- start `ExecutorRunner`;
- allocate the production execution-session slot;
- send an ADB command;
- mutate a device or host artifact;
- recreate the original execution;
- resume or replay the original run;
- create a sidecar execution identifier; or
- grant execution, device, root, review, or recovery authority.

The projected state is explicitly a qualification presentation of an already-terminal physical run.

### 5.3 React behavior

React renders the projection through the normal terminal execution/result components and recovery controls wherever possible. A qualification-only shell may select the subcase and accepted backend binding, but it must not duplicate the result UI.

The visible state must therefore inherit normal production behavior for:

- authored title and issue text;
- authored remediation;
- failed/cancelled terminal projection;
- completed versus **Not attempted** accounting;
- partial-change presentation;
- authority/requalification state;
- available recovery/navigation controls; and
- absence of resume/replay/checkpoint/ownership-transfer controls.

A small development-only label may identify the surface as Phase 6D.6 qualification so an operator cannot confuse it with a live execution.

## 6. Sanitized UI-state capture

### 6.1 Captured contract

The qualification capture action produces exactly the UI-state fields required by the existing `uiSmokeRecord` contract:

- `backendRunId`;
- `authoredTitle`;
- `authoredIssueText`;
- `authoredRemediation`;
- `terminalStepProjection`;
- `notAttempted`;
- `partialChangePresentation`;
- `authorityInvalidated`;
- `recoveryState`; and
- `availableControls`.

The capture must be derived from the actual trusted DTO/state currently rendered, not independently reconstructed from the manifest.

### 6.2 Capture artifact

Trusted code canonicalizes the UI-state object using the same deterministic key-order/digest semantics expected by the Phase 6D.6 validator and returns or writes a qualification artifact containing:

- `kind: ui_state_capture`;
- the exact UI-state content; and
- its SHA-256 digest.

If the implementation writes artifacts directly, it may write only beneath the fixed `docs/testing/phase-6d6/evidence/ui/` qualification location in a development repository checkout, with create-new semantics and safe generated filenames. React must not choose a destination path.

If repository mutation from the application would introduce unnecessary authority, the preferred alternative is for trusted code to return the canonical sanitized content/digest and provide a repository-owned development helper to create the final artifact. Either design must preserve the invariant that the artifact bytes are exactly the state that was displayed and digested.

### 6.3 Build identity

The bridge projects deterministic development-build identity/version/digest information required for the eventual composite record. The build digest must come from trusted application/build inputs and must not be supplied by React or typed manually by the operator.

The UI-state capture itself does not create the final `ui_smoke_composite` record. Final record assembly still requires the operator's artifact-bound observation and remains a deliberate manual evidence step.

## 7. Subcase mapping

Use the existing `uiSmokeContracts` and physical scenario categories as authority:

- **cancellation** → a passing `cancellation_active` or `cancellation_boundary` record compatible with the UI contract;
- **transport** → a passing `usb_disconnect_active` or `usb_disconnect_boundary` record; conditional `device_offline` cannot satisfy it;
- **root** → a passing `root_revocation` record;
- **storage** → a passing `low_storage` record;
- **host_sleep** → a passing host-sleep record compatible with the UI contract.

The bridge must not silently normalize a different backend issue into the expected UI-smoke issue. If the physical record's terminal branch cannot satisfy the current UI-smoke contract, that candidate is unavailable until the contract is deliberately changed or compatible evidence is collected.

Because manual host-sleep validation is deferred, no host-sleep candidate is currently expected to be eligible. The implementation should display that absence as an unavailable qualification binding, not synthesize a substitute from `operation_timeout` or deterministic host tests.

## 8. Error handling and failure modes

Qualification failures are development-only, sanitized, and fail closed. They must distinguish enough categories to debug the qualification flow without exposing raw evidence content or paths, including:

- qualification feature/gate unavailable;
- no accepted physical candidate for a subcase/repetition;
- evidence record invalid;
- evidence/trace digest mismatch;
- scenario category mismatch;
- issue-contract mismatch;
- projection inconsistency;
- capture state mismatch or digest failure; and
- create-new artifact collision if direct artifact writing is used.

No failure falls back to static UI text, a weaker candidate, or a fabricated record.

## 9. Automated verification

Implementation must add deterministic automated coverage for at least:

1. every qualification gate is required and ordinary debug/real-execution commands do not accidentally enable UI-smoke mode;
2. evidence lookup is confined to the fixed repository evidence location and rejects symlinks/path escapes;
3. only passing physical evidence is selectable;
4. physical category mapping is exact, including rejection of `device_offline` for the mandatory transport subcase;
5. backend run ID, trace digest, and issue-code mismatches fail closed;
6. absent host-sleep evidence stays unavailable and cannot be replaced by timeout/deterministic evidence;
7. normal production projection logic and the qualification bridge produce identical UI DTO fields for equivalent terminal facts;
8. React renders the normal terminal result surface rather than a separate copy of the failure UI;
9. forbidden resume/replay/checkpoint/ownership-transfer controls remain absent;
10. capture bytes are derived from the rendered trusted state and canonical digest verification detects any mismatch;
11. captured state recursively satisfies the existing sanitization policy;
12. build identity is trusted and not caller-supplied;
13. no ADB call, executor start, production slot acquisition, or runtime authority creation occurs while loading/capturing a qualification projection; and
14. existing Phase 6D.6 evidence validator/regression suites remain green and existing accepted evidence is byte-for-byte untouched.

Repository-wide formatting, tests, typecheck, lint, build, and strict Clippy gates applicable to the touched backend/Tauri/frontend paths must pass.

Ignored physical tests and manual GUI smoke must not be run in this implementation slice.

## 10. Documentation updates in the implementation slice

After implementation and automated verification, update current-state documentation to say only what is proven:

- UI-smoke backend binding/capture plumbing is implemented and ready for manual qualification;
- no UI-smoke repetition was run or counted;
- host-sleep and identity-replacement physical repetitions remain deferred/missing;
- Phase 6D remains **In progress**;
- Phase 6E remains **Planned**;
- accepted existing physical evidence remains unchanged; and
- repository-wide strict Clippy is no longer an outstanding Phase 6D.6 blocker if it still passes at implementation completion.

Correct stale statements that currently claim all physical evidence is absent, that the host-sleep deadline clock cannot be observed, that the active physical adapter lacks exact child evidence, or that strict Clippy is still blocked, but do not rewrite historical run results.

## 11. Scope boundaries

### In scope

- development-only trusted evidence discovery/binding;
- reuse/refactoring of production terminal/recovery projection logic where needed;
- development qualification presentation plumbing;
- sanitized UI-state capture/digest support;
- deterministic tests;
- runbook/current-state documentation needed to use the new plumbing later.

### Out of scope

- running any ignored physical Phase 6D.6 scenario;
- running either UI-smoke repetition;
- generating final `ui_smoke_composite` evidence without operator observation;
- accepting the same-serial replacement hardware limitation;
- Phase 6E recipe qualification;
- packaged-GUI or release qualification;
- changing production timeout values or safety semantics;
- adding resume, replay, rollback, checkpoint, automatic retry, reconnect, or ownership transfer;
- introducing arbitrary evidence paths, raw evidence access in React, or a generic terminal-state injection API.

## 12. Completion criteria for this implementation slice

The slice is complete when the repository can, under the exact development qualification gates, select an eligible accepted physical backend record, project it through production execution/recovery presentation logic, display that state in the normal terminal UI, and generate a canonical sanitized UI-state capture bound to the exact backend run/trace and trusted development build identity; all automated gates pass; no physical/manual evidence was collected; existing evidence was not altered; and documentation truthfully leaves Phase 6D **In progress** pending the deferred physical and UI-smoke repetitions.
