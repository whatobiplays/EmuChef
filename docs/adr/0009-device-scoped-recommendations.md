# ADR 0009: Device- and brand-scoped recommended setups

**Status:** Accepted product direction; recommendation evidence and implementation details open.

EmuChef's primary experience offers a small number of meaningful choices, recommendations, and sensible defaults with advanced settings progressively disclosed. Device Profiles identify hardware and capabilities. Device Plans own recommended Recipe composition and app-setting values for supported device models and brand families; App Definitions own setting semantics and validity. Applicability ranks exact model before brand family before a device-independent baseline. Equal-specificity recommendation-match ambiguity remains an error, not resolved by catalog loading order. **Device Profile identification happens first**: any two matching non-generic profiles require explicit current-session user selection regardless of match ranking, specificity or confidence. A generic fallback is not a competing non-generic profile. Model-specific settings cannot silently become global recommendations.

Compatibility requirements are enforced, while recommended values can be changed to other valid values. An unknown exact device may use only explicitly supported generic capabilities, not inferred model-specific settings. The consumer UI identifies the source of meaningful defaults and allows restoration of recommended values. An explicit valid user choice outranks device recommendations. At lower priority, exact-model recommendations outrank brand-family recommendations, which outrank generic baselines. Equal-priority property writes from different Recipes use the last writer in a deterministic, reviewed order; this rule does not override safety and compatibility requirements, or suppress equal-specificity device-match ambiguity errors. Saved valid explicit setting choices remain available for **the same confirmed Device Profile** after fresh applicability and target validation; invalid values require correction. Selecting a **different Device Profile starts a new setup**, with no automatic migration, carry-forward or cross-profile compatibility comparison. The old saved setup remains in the library under its originating Device Profile/Plan. Independently chosen app-owned library templates are not complete saved-setup migration. The existing `overrides.config_variants` entries are metadata only and cannot supply real planner bindings without implementing that capability.

## Open engineering contract (not implemented)

[EmuChef product realignment proposal](../product/emuchef-product-realignment-proposal.md) assigns T07 property semantics, T11 deterministic recommendation matching and sanitized provenance, and T05b profile-scoped saved intent revalidation. T09 resolves competing Recipe property intents for the same destination before review: explicit valid user values prevail; model over brand over generic; same-priority last writer follows a stable reviewed execution order. These are requirements, not operational claims about current metadata-only `config_variants`.


## Selection and saved-setup boundary (accepted 2026-11-15)

Device Profile *match* means observed Android facts satisfy authored eligibility criteria, not that the physical device's retail identity was uniquely established. A user selection resolves competing non-generic matches; it is confirmation without a second prompt. A single unambiguous profile can be selected automatically. Rust/Tauri binds the selection to current device session and catalog identity and invalidates it with explanation on material changes; stale frontend/default-plan/saved intent cannot restore authority. Profile switching clears the previous setup, while active or unresolved execution remains protected. See [ADR 0013](0013-session-bound-device-profile-selection.md).

The earlier carry-forward proposal treated saved settings as portable across *different* profiles and proposed warnings for incompatible overrides. That alternative is superseded because it would require an open-ended cross-device compatibility and migration mechanism and could retain stale target assumptions. The narrower same-profile revalidation rule retains useful saved intent without transferring setup state across hardware profiles. Recommendation precedence remains model > brand > generic **within** the selected profile, and same-priority final-property conflicts keep their separately reviewed deterministic order.
