# ADR 0007: Portable device storage targets and shared setup locations

**Status:** Accepted product direction; device identity and discovery proof details open.

User-selected storage destinations are logical Storage Targets combining a Device Storage Volume with a relative location, rather than embedding device-specific `/storage/XXXX-XXXX` mount paths in authored Recipes or saved setups. Initial coverage is internal shared storage and portable/removable SD cards; adopted/private storage and USB drives are deferred. If an SD card changes, EmuChef requires confirmation and a fresh destination review, rather than permanently pinning the original UUID or silently selecting another card. An absent or ambiguous SD card cannot silently fall back to internal storage. Volume identity and the resolved path are rechecked before execution.

A Setup Location names one user selection, such as a ROM library destination, reusable across Recipes and generated configurations. This differs from an app-owned App Target. SD-backed locations may be used for user content and application-supported configurable directories, but cannot arbitrarily redirect Android-managed installation or private app data. EmuChef checks the volume, mount state, write capability, and relevant application access assumptions; ADB copy success alone is not proof that an application can use files. When app-level usability cannot be established, report the uncertainty rather than claim success.

Saved setup intent may be reused on other supported devices. Valid explicit user choices persist, while device-specific recommendations, device identity, target volumes, and configuration paths must be re-evaluated and newly reviewed. Potentially inappropriate overrides require warnings and invalid choices require correction. Exact portable-intent retention, discovery trust, and proof standards remain design questions.

## Open engineering contract (not implemented)

[EmuChef product realignment proposal](../product/emuchef-product-realignment-proposal.md) assigns T04 volume discovery and identity, T05 shared logical binding, T05b reusable cross-device saved intent, T06a physical destination-access proof, and T06b separate emulator file-usability proof. Storage visibility and successful ADB transfer alone are not app usability evidence. The approved product requirement must not be presented as existing device qualification.

**Candidate feasibility is unresolved:** The current `ayaneo.pocket_air_mini` profile has `app_data_write: false`, while the App Target resolver uses this capability for both `app_data` and `external_app_data`. RetroArch's configuration and several required resource destinations use those locations. The planner's `repo_plan_e2e_no_app_data_write_contexts_prune_app_data_dependents` test allows a partial successful plan, pruning the final launch. T06a must establish an evidenced supported configuration path, resource path and complete milestone-required operation graph before T13b/T15 may qualify this candidate; T06b separately proves emulator usability. This is a candidate support limitation, **not evidence of physical inability** and not authority to flip a capability flag or weaken the milestone.
