# ADR 0006: App-owned configuration definitions and managed updates

**Status:** Accepted architectural decision. App-owned schema and standalone rendering are implemented; existing-file composition, complete consumer deployment, and physical qualification remain separate work.

App Definitions own an application's configuration format, property semantics, and supported, typed settings. An app-specific Recipe contains a `config` section with a base configuration file reference plus the subset of app-defined settings that users may configure or override. The Recipe owns option exposure, presentation, values, and orchestration but must not duplicate or redefine the App Definition's intrinsic setting rules. Device Plans provide model- or brand-scoped recommended values. Both catalog-provided and user-supplied Configuration Templates are supported under the owning App Definition's format and setting rules. The trusted runtime applies a deterministic pipeline: choose a template, substitute declared typed variables, apply direct property overrides, validate the result, safely merge explicitly managed properties when modifying an existing file, and prepare a reviewed artifact. Format-specific readers and writers can support key/value, INI, JSON, and other formats; a second application with a different format must test the abstraction. Arbitrary script execution and unvalidated whole-file text replacement are outside this trust boundary.

Configuring an existing supported app is independent of installation. When a configuration file already exists, a template is not blanket authority to replace its values: edits target managed properties only, preserving unrelated settings, comments, ordering, and formatting where the format supports it. Ambiguous or unsafe edits are refused, while independent setup work may continue. Unknown application versions do not by themselves block a configuration attempt; concrete format, parsing, editing, or access incompatibilities do block the dependent operation.

Users may reuse templates and explicitly retain generated configurations in a local library. A saved reusable file is not itself a reviewed execution artifact: every deployment freshly resolves device-dependent variables and produces a deterministic, immutable snapshot with content identity and intended destination for review. A relevant device-side configuration change after review invalidates the affected operation and requires replanning before writes. Reusable generated artifacts must not be deployed with stale device paths. Setting precedence is explicit user choices, then device model recommendations, brand recommendations, and generic baseline. When multiple Recipes write the same property at equal priority, the last writer in a deterministic, reviewed execution order wins; ambiguous equal-specificity device matching remains an error. In the consumer UI, ordinary and advanced options come from the app Recipe's `config` section and are limited to supported settings. Direct editing of arbitrary unsupported properties is not part of the normal UI. The app-owned configuration schema and deterministic standalone rendering are implemented; multi-Recipe file composition and the complete consumer preview/deployment workflow remain separate contracts.

## Implementation status and remaining contracts

[EmuChef product realignment proposal](../product/emuchef-product-realignment-proposal.md) assigns T07 to app-owned configuration schemas and Recipe `config` exposure, and T08 to typed substitution and standalone rendering. Both are implemented and their issues are closed (#48 and #51). The Issue #56 path implements native-authorized Create and full-file Replace for the exact RetroArch `config` App Target, with default private backups and a fresh report-bound waiver after backup failure. Host and fake-device coverage exercises the path; physical Android qualification and production enablement remain outstanding. T09 still owns existing-file safe merging and multi-Recipe composition (#54); T11 recommendations (#52), T12 the reusable configuration library (#59), and T13b the complete first-run/existing-app lifecycle (#61) remain separate work. This implementation does not complete those contracts or qualify the device. One validated, frozen artifact per destination and stage remains the intended composition boundary; exact publication guarantees require adapter evidence.

Distinct Recipes may also perform ordinary file-copy operations against overlapping destinations. That behavior follows T03's serial copy order and each operation's reviewed `merge`, `replace`, or `sync` policy, exact deletion set, predecessor result, and current destination preconditions. Shared paths alone do not establish a semantic conflict between Recipes. This file-copy contract does not compose managed configuration properties or authorize a generic overwrite of protected configuration files. T09 continues to produce one validated, frozen configuration artifact per destination and stage; any sequential publication must bind and review each intermediate state.

**Property admission and early publication scope:** T07/T08 reject unknown managed-property declarations, exposed-setting references, and direct property overrides. A safely parseable existing device configuration may contain unknown untouched properties; they are preserved, not rejected merely for lacking app-owned declarations. User-provided templates may contain unknown literal properties only as safely parsed opaque, unmanaged content under explicit format and file-safety bounds; this is distinct from validating managed settings. T13a's first end-to-end configuration slice is create-only for one writer, one supported destination and a **confirmed-absent file**; it must bind reviewed bytes to the destination and absence, revalidate, use a proven no-clobber create that rejects an appearing target, and verify or report a possibly changed/unverified outcome. T09 later extends the mechanism to existing-file merges and multi-Recipe composition. Issue #56 now supplies a narrow host-tested Create/Replace path. T09 still owns existing-file managed-property merging and multi-Recipe composition. Physical publication outcomes remain unqualified.
