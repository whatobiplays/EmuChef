# ADR 0006: App-owned configuration definitions and managed updates

**Status:** Accepted product direction; implementation contract and template pointer details pending.

App Definitions own an application's configuration format, property semantics, and supported, typed settings. An app-specific Recipe contains a `config` section with a base configuration file reference plus the subset of app-defined settings that users may configure or override. The Recipe owns option exposure, presentation, values, and orchestration but must not duplicate or redefine the App Definition's intrinsic setting rules. Device Plans provide model- or brand-scoped recommended values. Both catalog-provided and user-supplied Configuration Templates are supported under the owning App Definition's format and setting rules. The trusted runtime applies a deterministic pipeline: choose a template, substitute declared typed variables, apply direct property overrides, validate the result, safely merge explicitly managed properties when modifying an existing file, and prepare a reviewed artifact. Format-specific readers and writers can support key/value, INI, JSON, and other formats; a second application with a different format must test the abstraction. Arbitrary script execution and unvalidated whole-file text replacement are outside this trust boundary.

Configuring an existing supported app is independent of installation. When a configuration file already exists, a template is not blanket authority to replace its values: edits target managed properties only, preserving unrelated settings, comments, ordering, and formatting where the format supports it. Ambiguous or unsafe edits are refused, while independent setup work may continue. Unknown application versions do not by themselves block a configuration attempt; concrete format, parsing, editing, or access incompatibilities do block the dependent operation.

Users may reuse templates and explicitly retain generated configurations in a local library. A saved reusable file is not itself a reviewed execution artifact: every deployment freshly resolves device-dependent variables and produces a deterministic, immutable snapshot with content identity and intended destination for review. A relevant device-side configuration change after review invalidates the affected operation and requires replanning before writes. Reusable generated artifacts must not be deployed with stale device paths. Setting precedence is explicit user choices, then device model recommendations, brand recommendations, and generic baseline. When multiple Recipes write the same property at equal priority, the last writer in a deterministic, reviewed execution order wins; ambiguous equal-specificity device matching remains an error. In the consumer UI, ordinary and advanced options come from the app Recipe's `config` section and are limited to supported settings. Direct editing of arbitrary unsupported properties is not part of the normal UI. The exact file-pointer schema, preview presentation, and reproducible plan-merging contract remain implementation design questions.

## Open engineering contract (not implemented)

[EmuChef product realignment proposal](../product/emuchef-product-realignment-proposal.md) assigns T07 the app-document and Recipe `config` schema (including base-file and managed-property references, absent/empty/clear/reset semantics and non-lossy editor compatibility), T08 typed substitution and standalone rendering, T09 canonical per-file composition/safe merging/final-byte hashing, and T13a/T13b gated consumer integration and first-run staging. These are implementation requirements, not current schema or qualified runtime behavior. One validated, frozen artifact per destination and stage is preferred; exact publication guarantees require adapter evidence.

**Property admission and early publication scope:** T07/T08 reject unknown managed-property declarations, exposed-setting references, and direct property overrides. A safely parseable existing device configuration may contain unknown untouched properties; they are preserved, not rejected merely for lacking app-owned declarations. User-provided templates may contain unknown literal properties only as safely parsed opaque, unmanaged content under explicit format and file-safety bounds; this is distinct from validating managed settings. T13a's first end-to-end configuration slice is create-only for one writer, one supported destination and a **confirmed-absent file**; it must bind reviewed bytes to the destination and absence, revalidate, use a proven no-clobber create that rejects an appearing target, and verify or report a possibly changed/unverified outcome. T09 later extends the mechanism to existing-file merges and multi-Recipe composition. No such new publication behavior is yet implemented or qualified.
