## 1. Decision state, non-regression, and boundaries

The original Q1–Q46 product decisions, OEM-assisted decisions Q47–Q83, and UX-1 A are accepted product direction. ADRs 0005–0011 record their architectural boundaries; implementation and qualification contracts remain open until demonstrated. Product agreement does not itself authorize code changes, device operations, GitHub publication or release. Do not treat acceptance of a product requirement as an implementation or qualification result.

EmuChef proper is a guided installer and configurator for nontechnical Android handheld owners. Its primary path is connect/confirm one device, choose a supported model/brand recommendation, select apps and content, choose a few friendly per-app settings, review actual planned changes, and apply a qualified configuration. Simulation is optional, while explicit review and existing release/evidence gates remain mandatory. The app targets Apple Silicon macOS via native Tauri/React and the trusted Rust sidecar; React remains sanitized presentation only. Android SDK Platform-Tools remains user supplied, with the existing guided prerequisite/import workflow and no implicit SDK acquisition.

Separate authority domains:
- **App Definition:** app identity, artifacts, semantic App Targets, supported configuration document formats, recognized property identities, types, safe parsing/encoding/validation.
- **App-specific Recipe:** procedure and one `config` section naming a base configuration source and the subset of supported settings exposed to the user; no Recipe-wide implicit App ownership and no duplicated intrinsic validators.
- **Device Profile:** observed or authored device identity and capability constraints.
- **Device Plan:** app/Recipe composition and exact-model, brand-family, or generic recommendations. Exact match takes priority over brand over generic; equally specific matching ambiguity is an error.
- **Setup Location / Storage Target:** reusable logical volume choice plus relative location, distinct from App Target; user intent survives changed mount UUIDs.
- **Execution Plan:** resolved, immutable and reviewable authority for a specific target and stage, not a saved setup or reusable template.
- **Trusted runtime:** validation, planning, rendering, device access, write/recovery, preflight, and truthful results.
- **Configuration Library:** catalog and user templates plus explicitly retained generated files, not current execution authority.

Setting provenance: valid explicit user choice > exact-model recommendation > brand recommendation > device-independent default. Where two Recipes contribute the same property at the same priority, the later writer in a deterministic, reviewed operation order wins. Device matching ambiguity, safety/compatibility requirements, and invalid user choices are never silently resolved with last-writer priority. The user can see the significant source of a recommendation and restore it. Unknown app versions are attempted optimistically until concrete incompatibility is observed; unsafe parsing/merging still blocks the affected change.

Existing accepted requirements remain active: accessible keyboard/screen-reader/reduced-motion/zoom UX; sanitized React projections and reports; sensitive-input privacy; portable intent and crash-draft recovery; bounded diagnostics; cancellation, identity, timeout, root, storage, and transport protections; no automatic resume/replay or whole-setup rollback. Real execution remains feature gated and disabled in ordinary production. Independent operations may continue after an ordinary dependency failure only when allowed by the current failure model; transport loss and timeout remain session-fatal.

## 3. Configuration schema, composition, and review contract

The schema is **not implemented**. Its exact representation is to be closed by T07–T09.

1. **Definition and references (T07):** App Definitions declare configuration documents, canonical property identities (including section/path and format rules), supported types, validation and app-owned destination identities. App Recipes declare `config` blocks with a reference to the base file/template, the related app document, chosen managed properties, UI labels/grouping, and explicit target App references. References must be validated without duplicating intrinsic application facts in Recipes.
2. **Input semantics (T07):** Distinguish *absent* (no authored opinion), typed explicit empty value (only if valid), *clear* (remove a managed property where permitted), *reset* (recompute the device recommendation), and authored defaults. Reject unknown or invalid **managed-property declarations, exposed-setting references, and direct overrides**, and invalid managed values/types/ranges; never reject a safely parseable existing configuration solely because it contains unknown **untouched** properties. Preserve unknown existing content unless a concrete incompatibility blocks the requested edit. Explicit user choices cannot disable mandatory compatibility requirements. Preserve trusted provenance and sanitized review.
3. **Typed rendering (T08):** Resolve catalog or user base-template source and trusted identity, typed declared variable sources, format-aware escaping/serialization, direct property overrides, and logical Setup Location references. No arbitrary scripts or unchecked string replacement. Re-resolve volume/device-dependent values per execution. Test a distinct second-format fixture during foundation work; that is not full second-app qualification.
4. **Per-file composition (T09):** Identify a configuration destination canonically by resolved device, volume, app target and normalized file path (including alias/overlap checks). Group all Recipes writing a given file in one stage. Resolve precedence and duplicates in a stable reviewed order **before** rendering. A different file must not be affected by a property merge. Prefer **one composed final artifact per destination per stage** rather than individually pushing one artifact per Recipe. If a tested adapter requires sequential publication, specify each intermediate expected hash/state and review it; no unreviewed intermediate behavior.
5. **Read/merge (T09):** Inspect a quiescent existing file or confirmed absence without mutating the device during planning. For existing files, modify only managed keys; preserve unrelated values, comments, ordering and other format semantics. If preservation is ambiguous or impossible, block this configuration operation and permit safe independent work. Config templates never implicitly replace a user's whole file. Unknown app versions do not prohibit safe editing.
6. **Reviewed artifact (T08/T09):** Validate the **actual final composed bytes** after merging. Freeze/hash the exact output and bind it to the canonical destination, relevant app/volume identity, and the reviewed original-file content hash **or confirmed absence**. T13a accepts **confirmed absence only**; existing original content and multi-writer final-state composition belong to T09. Show changed properties and effective sources, notable preserved content, backup status, and expected file effects without exposing raw sensitive paths to React. Relevant target changes invalidate review, including a change during consent/backup delay. Recheck at the last safe write boundary.
7. **Publication and verification (T13a minimum; T09/T13b generalization):** **T13a** supports one writer, one supported destination, **confirmed-absent target only**, and no existing-file overwrite or general multi-Recipe composition. Freeze the exact reviewed bytes/hash, canonical destination, device/path identity, and confirmed absence; revalidate applicable device, capability, path, and target-state preconditions. Publish via a **proven create-only/no-clobber mechanism** that refuses to overwrite even if a target appears *between the last observation and publication*; observing absence followed by unconditional overwriting ADB transfer is forbidden. A newly appearing/existing target is stale and requires fresh planning/review. Verify exact published bytes or report **possibly changed/unverified** if the attempt's final state cannot be established. **T09** generalizes this to safe existing-file merges, per-destination composition, revalidation after consent/backup, and supported publication mechanisms. No remote atomicity claim without adapter and physical proof. If independent no-clobber creation is unavailable, retain early UI/planning integration but explicitly block T13a gated deployment/G1 on the necessary bounded T09 publication work.

**Unknown literal property admission (T07/T08):** A user-supplied template may contain unknown **literal** properties only if the supported format parser can safely retain them as opaque, unmanaged content within encoding, size, ambiguity, and security constraints. Such literals do not acquire managed-setting validation or expose an override UI; undeclared placeholders and direct overrides of unknown names remain invalid. Reject unsafe/malformed template content. This admission rule is distinct from the requirement to preserve untouched unknown properties already present in a device configuration.

**Mandatory composition tests:** two disjoint Recipe edits survive in the same generated file; two writes to the same property select the accepted priority/winner; reordering catalog enumeration does not change result; an explicit valid user choice survives a conflicting device recommendation; a matched device ambiguity errors; default/absent/empty/clear/reset are distinguished; the backup captures the intended original file and the plan's frozen final bytes match the deployed content where verification is possible.

### 3.1 New installation and first-run lifecycle (T13a/T13b)

The **current** `app.retroarch.provision` Recipe installs APK if needed, launches/waits/stops RetroArch to bootstrap defaults, applies permissions, launches/waits/stops again, then optionally seeds `retroarch.cfg` and finally launches the app. Its current config input is an optional *supplied file*, not a generated one. The seed step depends on post-permission stop, while final launch does not explicitly depend on the seed step. An implementation ticket must introduce explicit ordering and failure-dependency edges rather than rely on file order.

| Observed scenario | Proposed reviewed behavior |
| --- | --- |
| Already-installed app with existing, quiescent configuration | Read/identify/hash original; compose validated managed delta; one review may authorize the bound update if no earlier lifecycle action can modify the file |
| Already-installed app with no configuration | Review confirmed absence and generated new file; use single stage only if app-side initialization is not required or all file preconditions are knowable |
| Already-installed app currently running or otherwise not demonstrably quiescent | Review and authorize any required stop/preparation action; execute it; inspect **post-preparation** app state and current config bytes/absence; generate a new configuration plan and review. No hidden stop during planning and no reuse of the pre-stop snapshot |
| Fresh install whose first run creates configuration | **Stage A:** review installation, permissions and required bootstrap actions; apply and truthfully report. **Stage B:** re-probe newly initialized app storage, inspect new file or verified absence, compose exact config bytes, review again, then deploy |
| App start or stop changes configuration | Any lifecycle action that can write the config invalidates earlier assumptions; inspect again before planning or verify after publication without automatic replay. **Example:** stopping a running app flushes changed preferences; the subsequent review must bind to the post-stop bytes, not a pre-stop hash |
| Install succeeds; config is blocked or fails | Retain truthful installed-app success and blocked/failed configuration result. No hidden resume, uninstall, or automatic rollback; offer explicit "Finish configuration" after fresh re-probe and new review |

**App-state precondition (T13b/C06):** Establish qualified quiescence through observable supported app/process state, completion of any explicitly reviewed preparation, and a fresh target-file hash or confirmed absence. Bind that observation to the reviewed stage. App launch/stop/initialization, outside edits, process-state uncertainty, target/permission changes, or file drift invalidate it; re-observe and re-review. A stop may itself write the file: never treat a pre-stop snapshot as current. **Restoration is subject to the same relevant quiescence and stale-target checks**, with reviewed preparation if needed. No planning-time hidden stop or device mutation.

**Preseed optimization:** A single-review fresh-install path is allowed only when target existence/content and final desired bytes are knowable before any mutation, bootstrap cannot create conflicting content, and the exact app/build/adapter is qualified for that sequence. Otherwise, review Stage A, perform it, read Stage B state side-effect-free, and show a second review. Never silently generate/merge new bytes during execution or mutate the device as an undisclosed "planning" probe.

**Accepted UX-1 A:** Show **one guided "Set up RetroArch" journey**. Review installation/initialization as Stage A; when first-run defaults produce previously unknown bytes, inspect them and present **"Finish configuration"** with a fresh explicit review/apply as Stage B. Keep any further OEM-script/ADB stages in the same journey, refreshing review when observations invalidate previous authority. Preserve truthful installed status if later configuration stops. Never silently run privileged scripts or merge unreviewed bytes.

## 4. Explicit copy semantics and cross-Recipe safety (T03)

Use source folder `/host/ROMs` containing `A.rom` and `B.rom`; existing device destination `ROMs` contains an old `B.rom` and unrelated `C.rom`.

| Intent | Exact scope / result | Review requirements |
| --- | --- | --- |
| **Add or Update** | Add `A.rom`, update matching `B.rom`; preserve unrelated `C.rom`. Never delete destination-only children | List additions and replacements; preflight collision and changed-state policies |
| **Replace Destination** | Explicitly replace the **selected destination file or directory tree** with source content. The resulting selected `ROMs` tree has only A and B; an ancestor such as `Emulation/` and sibling folders are out of scope | Show exact selected destructive boundary and existing contents affected, not just a generic warning |
| **Mirror** | Make the selected destination tree match the source, including deleting destination-only `C.rom`; final content A and B | Enumerate deletion manifest, show count and expandable paths, and revalidate full relevant source/destination state immediately before irreversible work |

Mirror is **not** equivalent to ADB `push --sync`: that flag updates newer files and does not delete extras. Fake and real execution must share the same semantic contract and qualification; the current fake/real mismatch is a foundational defect. Replace must never delete parent directories or sibling content by implicit path inference. All three modes must reject unsafe traversal, aliasing, self-copy, symlink escapes, or unproven boundaries as appropriate.

T03 must also define staged transfer and verification **before irreversible deletion where supported**, interruption and partial-outcome classification, manifest drift handling, no unreviewed deletion expansion, and overlapping destinations across Recipes. If one Recipe would Mirror or Replace a directory containing another Recipe's BIOS files or generated config, planning must detect the destructive overlap and either construct a single explicit reviewed operation preserving the intended files or block until the user corrects the setup. Last-writer-wins for config **properties** does not grant authority to silently delete a different Recipe's files. Do not assume remote directory operations are atomic.

### 5.1 OEM-assisted privileged setup on non-rooted devices (accepted direction Q47–Q83; not implemented)

**Relationship to the existing Recipe system:** OEM-assisted execution is a second **execution strategy for the same typed Recipe operations**, used when direct ADB root is unavailable at planning time. It is not a separately authored Recipe family, and existence of an OEM script menu **never** grants the ADB executor `root_shell` or `app_data_write`. Every root-privileged typed action otherwise supported by EmuChef's direct-root executor must be representable by the generated-script strategy, including protected-file copies, reads and conditions, authorized permissions/app-ops and supported ownership/mode operations. Unsupported required operations fail planning rather than being silently pruned; no arbitrary Recipe-owned shell text is admitted.

**Capability ownership and initial availability (Q47–Q48, Q55–Q57, Q63):** A Device Profile owns an independent OEM Root Script Runner capability, runner type, device-menu instructions, permitted internal shared-storage staging location and relevant invocation constraints. Shared manufacturer defaults can reduce duplication. Profiles are device-scoped, **not firmware allowlists**. Initial feature availability covers AYN, Retroid and AYANEO where the corresponding declared Profile applies and the user confirms the OEM menu exists. Unregistered devices first need a Profile; availability is not inferred solely from a matching brand and does not require a model-by-model rollout gate. Representative runner qualification remains necessary, while every claimed complete setup must still satisfy its own support/evidence requirements.

**Root detection and method selection (Q64, Q65 A+C, Q74 A):** Reuse current valid device/runtime-bound direct ADB-root qualification; otherwise automatically run a bounded root-availability check during **EmuChef proper** planning for the selected device. A confirmed denied/unavailable root result permits OEM strategy selection if the Profile supports it. Inconclusive/transport failures **fail closed** rather than establish unavailable root. This proposed automatic planning check does **not** alter Config Editor's existing explicit-only root probing policy. Prefer verified direct ADB root when available. The reviewed plan fixes the selected strategy. If ADB root becomes unavailable after review or during direct-root execution, fail closed and require a new reviewed plan rather than silently switching to OEM. Never promote OEM runner presence into direct ADB-root capability.

**Staging and trusted source (Q49–Q51, Q58–Q59, Q73 B):** Compile eligible privileged operations from the validated typed manifest into a script, then stage only that stage's necessary inputs, including protected-target payloads and shared-storage files participating in privileged operations. Independent ordinary ROM/file copies remain normal ADB operations. Stage in a distinct, run-owned, device-profile-approved **internal shared-storage directory** (for example a confirmed `Download/EmuChef/<run-id>` location); do not assume an arbitrary hard-coded `Downloads` path or removable SD compatibility. Bind script, manifest, file hashes, intended device/targets and stage/run identifiers to the reviewed authority. Revalidate staged bytes and protected preconditions at execution where feasible; reject known mismatch. OEM scripts may return bounded structured root-only inspections or explicitly requested read-back artifacts. Do not bulk-export unrelated private data. Necessary staged inputs do not require extra sensitive-content prompts beyond the ordinary review. Script self-checks cannot prove the OEM runner itself is trusted.

**Strictly sequential alternating stages (Q60, Q66, Q68, Q78 B):** Preserve the normalized Recipe dependency graph. Consecutive eligible root actions may be grouped into an OEM script stage; a setup may alternate `OEM stage A → ZIP import/reconciliation → ordinary ADB actions → OEM stage B → ZIP import/reconciliation` repeatedly until all work is complete. **No concurrent Recipe execution**: while an OEM stage is awaiting the user, running, or being reconciled, **all other Recipe steps pause**, even otherwise independent ADB actions. Bounded observation, identity checks, ZIP transfer and owned-artifact cleanup required for reconciliation are allowed, but they are not additional Recipe operations. Once the barrier resolves, ordinary ADB steps may resume serially under still-valid reviewed authority. A failed action blocks dependent actions; independent safe actions may continue **only after** reconciliation and under current fail-stop/session rules. Give an overall setup review plus a fresh stage review if new results, bytes or preconditions invalidate earlier approval. No hidden root invocation, automatic replay or plan resurrection across restart.

**User-mediated execution, ZIP results and verification (Q52–Q53, Q61–Q62, Q69–Q70):** EmuChef shows the reviewed bundle with profile-specific directions, then records an explicit `awaiting action on device` state. The user launches the script from the OEM menu. **Every separate script invocation produces a distinct immutable ZIP results archive (Q82 A)** in an owned results directory **separate from staging**, with a unique attempt identity plus the reviewed plan digest, stage/run/device identity, operation IDs/outcomes, artifact hashes and bounded sanitized logs. Later attempts never overwrite previous attempt evidence. EmuChef reconciles **all observed attempts** rather than trusting only the latest outcome. EmuChef pulls and safely parses the archive with strict count/size/decompression/path-entry/schema/hash limits, then checks independently accessible target postconditions. Protected-only checks require another expressly reviewed root inspection stage when needed. A ZIP receipt is script-reported evidence, **not independently verified protected-file state or emulator usability**. Missing, malformed or mismatched archives make the stage unresolved/unverified and block successor execution until explicit reconciliation or freshly reviewed repair. Reconnect or restart retains only non-authoritative run/owned-path pointers and never automatically relaunches the script or the old plan.

**Rerun behavior (Q67 B, Q75 A):** Prefer idempotent typed actions with local state/precondition checks. A user may rerun a script; an already satisfied operation can safely skip. If an action cannot safely repeat, or the state after an interrupted/partial run is unknowable, refuse that operation and require new reviewed intent. Do not impose a blanket one-shot lock, and do not pretend that later staging cleanup prevents double invocation while files remain present. Each invocation has an immutable result identity; already-satisfied typed actions may skip while unsafe/unknown repeats refuse and require a new review.

**Post-publication OEM invocation-admission closure contract (T18/T19/T13b):** The exclusive active guard and start-result reconciliation alone do **not** stop a new manual invocation after barrier release if cleanup fails and a script remains. T18 must provide a **device-enforced admission window** for each frozen reviewed bundle: `open` permits safe state-checked serial reruns while the stage barrier is held; `closing` denies new admissions while admitted attempts drain; `closed/revoked` permanently denies mutation by that bundle, even when its script remains on-device. **Script admission and device-side closure must be atomic relative to one another:** a racing invocation either is admitted (and reconciled) before closure or is rejected before mutation. A host-side flag, ZIP, acknowledgement or attempted deletion is not proof of revocation. The exact mechanism is an engineering obligation, not prescribed by this proposal.

T19 must establish **admission closure first**, reconcile every definitely or possibly started invocation and any separately reviewed root-only inspection *within the still-held barrier*, then prove no active/uncertain invocation remains **before** releasing the barrier or permitting ordinary Recipe successors. Failure to establish closure leaves `admission_closure_unverified` and the normal fail-stop behavior; it is **not** a Q81 C cleanup warning. Preference invalidation racing start, cancellation/replanning, superseded/replacement bundles and app restart/reconnect must use the same close/revoke-and-drain protocol; a host restart must never re-admit an old bundle. Every admitted invocation retains the frozen reviewed content, target, strategy and backup mode. **Q81 C remains unchanged after proven closure:** a failed eligible-artifact deletion is an independent warning with `cleanup_pending` and retry, not a reason to block a reconciled setup. T18/T19/T13b integration tests must include a closure/start race; success → proven closure → failed cleanup → barrier release → retained script manually launched (no mutation); preference invalidation racing start; restart/replacement without old authority; and Q81 C valid continuation after closure.

**Device hygiene and lifecycle (Q54, Q71 B, Q72 A, Q76–Q77 A, Q80 A):** The script **does not self-delete staging**. After the user acknowledges running the stage, EmuChef imports and validates the ZIP to protected host-side report storage and, when the bundle is no longer needed for that stage, **automatically removes** the corresponding run-owned device staging files. Later independent emulator usability verification may use retained host-side evidence; deletion itself does not imply success. The ZIP and error logs are in a **separate results directory**, so removing staging does not destroy them. After successful host import, clean the device-side ZIP and other no-longer-needed EmuChef results/temp artifacts using strict path/ownership guards. ## 6. Backup, restoration and result model (T10/T13)

- **Default:** per-file backup of original bytes before modification in protected, bounded storage; secure metadata and exact original-target identity. A changed target or stale approval is not silently overwritten.
- **When backup is enabled but fails:** explicit waiver for the affected file **and execution**, after warning. Declining blocks its update, not independent safe work.
- **Persistent opt-out (Q46 A):** separate confirmed Advanced preference, default off; while enabled, do not attempt automatic backups and do not repeatedly request per-file waivers. Every relevant review clearly displays "Configuration backups disabled". Re-enabling restores normal backups for new executions.
- **Reviewed effective backup mode (T10/C07):** Capture effective mode in the immutable reviewed execution/digest. Changing the persistent preference before an unstarted reviewed attempt invalidates the affected review. Once an OEM bundle is reviewed, **every admitted invocation of that same open bundle** retains the frozen mode; only a **newly reviewed** bundle may adopt changed preference after the old bundle's admission is proven revoked/drained. A per-file failure waiver binds to that file/execution. Global opt-out means **no automatic backup attempt or repeated per-file waiver** for an execution prepared under that mode.
- **Recovery:** enumerate eligible backups after app restart, validate provenance, target identity, current content and permissions, preview which current bytes restoration would overwrite, require a fresh reviewed restoration action and revalidate before write. No old plan or one-shot handle can silently resume. Provide retention policy and user-controlled cleanup without leaking sensitive content.
- **Interrupted write:** state the adapter's actual staging/durability guarantees; record any uncertainty, even when a transfer command exited unexpectedly. A post-write verification failure may mean bytes changed; never report it as clean rollback.

| Condition | Truthful configuration outcome |
| --- | --- |
| Final bytes equal observed existing file | No-op; no destructive write or unneeded backup |
| File absent where plan expected content, or observed content changed | Stale/precondition rejection; fresh planning and review required |
| Target appears after create-only review, including at publication race | Refuse to overwrite, reject as stale and require new plan/review; if a write may have occurred but cannot be verified, report possibly changed/unverified rather than success |
| Dependency blocked or unsupported permission | Blocked/not attempted; dependent actions do not run |
| Backup failure and consent declined | Configuration blocked; independent safe actions can continue |
| Write succeeded and exact final bytes verified | Confirmed updated/created |
| Write was attempted but final bytes cannot be verified | Possibly changed / unverified, with explicit recovery path and no invented rollback |
| Session-fatal transport loss or timeout | Preserve current fail-stop model: terminate further relevant work, invalidate authority, expose partial-change uncertainty and require fresh session/review |

The current `docs/architecture/planner-executor.md` accurately says **no backup or restoration contract exists today**. T10 must update it only once the new bounded capability is implemented and qualified; this proposal must not falsely claim otherwise.

## T01 approved engineering clarification register

This section cross-references the normative [EmuChef requirements](emuchef-requirements.md) and the updated ADRs. It is a **contract responsibility map**, not a new product decision or proof of implementation.

- **Reviewed execution vs invocation:** One reviewed execution may contain multiple reviewed stages; an OEM stage creates a frozen bundle. Each invocation of the **same** bundle inherits reviewed bytes, target, strategy and backup mode even when settings change. Only a new reviewed bundle can carry a changed preference.
- **Start/admission:** A staged `awaiting action on device` bundle is not started.
