# EmuChef Product Requirements — Accepted Q1–Q83 and UX-1 A

**Status:** Normative **product intent**, approved for documentation and GitHub tracking cutover on 2026-10-25. **Implementation and physical qualification are not implied.**  
**Scope:** EmuChef proper on Apple Silicon macOS; shared trusted Rust/Tauri runtime as needed; Config Editor feature development remains deferred except compatibility work that prevents loss of authored data.  
**Authority:** This document governs *what must be true*; accepted [ADRs 0005–0011](../adr/) explain architectural choices; [architecture contracts](../architecture/) describe *implemented behavior* until the approved changes land; [qualification obligations](qualification-obligations.md) and the evidence validators govern *proof*. ## 1. End-user path and ownership

- One guided, accessible **Set up <app>** journey: identify/confirm one supported Android handheld; choose compatible apps and model/brand recommendations; choose ROM/BIOS content, logical internal/SD Setup Locations and a few exposed app settings; review the **exact planned impact**; execute **only on supported qualified target/strategy and with explicit review**; report completed, failed, skipped, possibly changed/unverified and cleanup-pending results truthfully.
- **UX-1 A:** Newly installed apps may create defaults on first launch. Review and run initialization, then freshly inspect defaults and present a second review for the derived configuration. The same journey can alternate multiple reviewed OEM-script and ADB stages. Installing an app successfully while configuring it fails remains truthful partial success; never imply rollback or automatic replay.
- Simulation is an **optional aid**, not a mandatory prerequisite. Real execution remains compile-time/feature gated, off in ordinary production, and requires separate device authorization, exact evidence and eventual release authorization.
- The trusted Rust/sidecar/Tauri boundary alone resolves files/devices and holds execution authority. React gets sanitized user-facing projections and opaque handles. Platform-Tools are user-provided, not bundled or silently acquired. No generic user-authored shell executor.
- App Definitions own intrinsic identity, App Artifacts, App Targets, supported configuration documents and managed-property types/validators. A Recipe owns the procedure and app-specific `config` section exposing selected managed settings and a base configuration source. Device Profiles own device facts/capabilities, including the OEM runner declaration; Device Plans select app/Recipe composition and scoped recommendations. An immutable **reviewed Execution Plan** is the single deployment authority, not a reusable saved setup.

## 2. Recommendations, storage, content and configuration

- **Recommendation precedence:** valid explicit choice > exact model > brand > generic. Equally specific conflicting device matches are an error. At equal precedence, conflicting managed-property writes use **last writer in the stable reviewed order**, with provenance visible; a compatibility requirement cannot be overridden away. Restore recommendation by explicit action.
- **Portable storage:** discover and identify internal and removable SD separately; use logical Storage Targets and named Setup Locations, never portable saved literal mount bindings. Confirm changed, absent, ambiguous or unusable SD cards and renew review. Verify host/ADB accessibility **and separately** app-side ROM/BIOS/config usability. No silent internal fallback or redirection of Android-managed app installation/private data to SD.
- **Copy intent:** Add/Update preserves destination-only content; Replace replaces the selected file/tree and never its unselected parent/siblings; Mirror deletes destination-only contents only within the reviewed boundary. Preview actual deletions and cross-Recipe overlap, then recheck before deletion. ADB `push --sync` does **not** implement Mirror. Simulated and real semantics match. Independent safe actions may continue after ordinary dependency failures, subject to session-fatal transport/identity/timeout rules and OEM strict-stage barriers.
- **Templates:** app-owned schemas validate managed-property declarations, exposed-setting references and direct typed overrides. An otherwise safely parseable existing file may contain **unknown untouched properties**; preserve those along with comments/order/unmanaged content. User-template unknown literal properties are admitted only under an explicit bounded opaque-literal parsing/encoding rule. Reject unsafe or ambiguous format, duplicated managed names, unsupported managed overrides and unescaped/undeclared template substitutions.
- Render catalog/user templates with declared typed variables, safe escaping and direct managed-property edits. Coalesce multiple Recipes targeting the same canonical file into one deterministic **final artifact per destination per reviewed stage**; bind final-byte hash, original-file hash/**confirmed absence**, target/device/volume identity, and resolved settings/provenance. Recheck changed state before writes; do not claim remote atomicity without adapter evidence.
- **Early G1 thin slice:** exactly one writer, one supported destination, **confirmed-absent create-only** target. Use race-safe no-clobber publication even if a destination appears between last observation and actual mutation; reject a newly appeared file and require new review. Verify exact final bytes or report possibly changed/unverified. Existing-file safe merging and general multi-Recipe composition are later T09 contracts, not hidden shortcuts. If the adapter lacks independent create-only support, G1 deployment waits for the narrow T09 prerequisite without delaying early UI/planning.
- Existing installed apps may be running. If quiescence is unqualified, **review** required stop/preparation first; after it finishes, observe new app state and file bytes (which may have changed on stop), then create a fresh review. Apply the same app-state checks to restoration and later lifecycle actions.
- Reusable library: templates and explicitly saved generated artifacts persist as **portable intent**, not retained executable authority; re-render against the current target and use the **same** composition, review and deployment path by G4. Backward compatibility with pre-v1 debug-only saved setups is not required; never silently lose user-authored documents. Config Editor must round-trip new fields faithfully **or refuse unsafe saves**, without resuming editor feature work.

## 3. Backups, consent, recovery, and execution-admission boundary

**Effective backup mode** is part of the immutable reviewed execution and every reviewed OEM stage/bundle. It can be **enabled** (default) or **globally disabled** after confirmed Advanced Settings opt-out. When disabled, review visibly says `Configuration backups disabled`; the execution makes no automatic backup attempts and does not repeatedly prompt for per-file waivers. Re-enabling affects **newly prepared and reviewed bundles** only, never later invocations of the same reviewed bundle.

A **Reviewed Stage** authorizes the exact content, target, operation graph, backup mode and permitted execution strategy. Its **Staged Privileged Bundle** freezes those values. A **Privileged Execution Attempt** is one separate user invocation of that same reviewed bundle; it gets a unique start identity and immutable result evidence. Rerunning the *same* bundle inherits the identical reviewed content/backup mode, regardless of later preference changes. Only a **newly prepared and reviewed bundle** can use a changed preference or new file bytes.

**Admission/start:** For ordinary ADB execution, the trusted executor's accepted start/operation boundary governs. For OEM execution, preparing/staging a bundle and entering `awaiting action on device` are **not** proof of invocation start. Start is when the manufacturer runner actually begins the script, observed by the run-bound start journal/receipt protocol (T18/T19) and reconciled on reconnect. A user click saying "I ran it" is not sufficient to prove or time the start. When a preference changes while a bundle awaits action, **atomically close/revoke its device-side invocation admission**, reconcile any racing start and invalidate review; only a newly reviewed bundle may use the changed mode. A missing started marker or host-side flag is not closure proof. If invocation might already have started but its evidence is delayed/missing, mark **start uncertain** and fail closed: reconcile before deciding whether the prior mode was in force, never silently change it or authorize a different mode for an old bundle. New attempts on the **same** reviewed bundle never adopt a new preference. A running attempt cannot change its backup mode mid-flight.

**Backup-enabled existing-file modification:** Preserve a qualified, identity-bound original before overwrite. Backup success permits the reviewed update. If a per-file backup fails, **stop before any overwrite** and report a blocked operation; the user may grant a distinct, informed **file- and execution-specific waiver** only in a freshly reviewed continuation/bundle. The manual root script must not continue into an unapproved overwrite on backup failure. Declining blocks that file's modification; the ordinary dependency model and independent stage rules apply. A blanket opt-out bypasses backup attempts/waivers only when that mode was already reviewed for this bundle. Never imply whole-device or whole-setup transaction rollback.

**Recovery Original** is the protected original bytes plus sufficient target identity, hash, app/volume provenance and restoration metadata in the **qualified recovery store**, different from temporary payloads, ZIP results and staging. If the only copy of a required original is on device staging, preserve/verify it in the qualified store **before it becomes cleanup-eligible**. ZIP success does not prove originals are restorable. Restore via a fresh target inspection, verified app quiescence, previewed overwrite, fresh explicit review and safe publication. Original retention bounds, target guards and crash/partial-write reporting are part of T10/T13b evidence.

## 4. OEM-assisted execution of the same Recipes (AYN, Retroid, AYANEO)

- An **OEM Root Script Runner** is a distinct Device Profile capability, with runner instructions and supported internal shared-storage staging location. Manufacturer defaults may be reused. It never elevates `root_shell`/`app_data_write` for ADB; no firmware allowlists or mandatory per-model rollout gates. Eligibility requires a matching profile and user-confirmed OEM runner presence. Representative runner protocol proof and target-specific workflow qualification are **separate**.
- EmuChef proper planning reuses valid current root qualification, otherwise automatically runs a bounded root availability probe. Confirmed root available → direct-root strategy preferred; confirmed denied/unavailable → OEM option when profile supports it. Inconclusive/transport results fail closed. Config Editor's explicit-only authoring probe remains unchanged. **The reviewed strategy is frozen**: losing direct root later fails closed, requiring new planning/review; never switch to OEM mid-run.
- **T18 typed action parity:** every root-supported typed operation must compile to the OEM strategy, including protected reads/conditions and writes, declared app permissions/app-ops and supported metadata. Required predicates—target state, no-clobber create-only, quiescence, backup, stale guard, access/identity and any operation-specific safety check—must be **established by the chosen strategy** before mutation. "Where feasible" is never a waiver of a mandatory precondition. Unsupported operations fail planning, not silently prune required graph steps. No arbitrary script fragments.
- **T19 alternating stages:** valid overall review → one or more grouped OEM actions → run results reconciliation → serial ordinary ADB actions → potentially another OEM stage. While an OEM stage awaits device action, runs or is being reconciled, **no other Recipe operation** executes. Bounded verification, root-only inspected recovery within the same barrier, ZIP import and owned-artifact cleanup are reconciliation work, not permission to run ordinary successors. Any required root-only inspection is separately reviewed and retains its own invocation evidence. Result-dependent final-byte changes force fresh review. No automatic replay after restart.
- **Invocation protocol:** Each invocation has an immutable attempt identity and **start** as well as completed/interrupted/uncertain evidence, ordered by a device-side exclusive, monotonic run journal or an equivalently proven ordering authority, **not ZIP arrival order or untrusted wall timestamps**. A bounded active guard prevents **concurrent privileged mutation** by a repeated invocation while allowing safe serial reruns. Repeated satisfied idempotent actions skip; unsafe/unproven reruns refuse and require a new review. A first completed ZIP followed by an interrupted second attempt is **not** a proven final success. Reconcile all started/observed attempts before releasing the OEM stage barrier or deleting needed staging. A new ZIP per invocation preserves prior errors and partial results. A missing/malformed/late ZIP means unresolved/unverified until reconciled, and dependents remain blocked.
**Device-enforced invocation admission and closure (T18):** A Reviewed OEM Bundle has a device-enforced admission window bound to its plan, stage, device, strategy and frozen backup mode. While `open` with the OEM barrier held, **safe, state-checked serial reruns** of the same bundle are permitted. Each actual script start must atomically test that admission remains open, claim the exclusive mutation right and record a distinct invocation start. Moving to `closing` or `closed/revoked` must be **atomic relative to script admission**: a racing start is either admitted before closure and must be reconciled, or rejected **before any mutation**. The mechanism is T18 engineering work; an exclusive active guard alone, a host UI flag, acknowledgement, ZIP arrival or requested file deletion does **not** prove revocation. A retained script of a closed/revoked bundle must refuse all subsequent mutation, even if cleanup fails.

**Barrier closure and drain (T19):** Before the OEM stage barrier releases, establish and prove device-side admission closure against new starts; reconcile every definitely/possibly admitted attempt and bounded separately reviewed root-only inspection **under the held barrier**; and establish that no attempt is active, incomplete or start-uncertain. The ordering proof must not depend on ZIP arrival order. If a racing start or closure cannot be proven, retain `admission_closure_unverified`, block successor Recipe work and preserve the existing fail-stop rules. A completed first invocation followed by an interrupted second remains unresolved. Closing the host UI or attempting cleanup does not close admission.

**Invalidation uses the same authority protocol:** Backup preference changes, cancellation, replanning, superseded/replacement bundles and restart recovery must close/revoke old device-side admission and reconcile possible starts before allowing replacement authority. No host restart reconstructs an old bundle's admission. Any admitted attempt retains the original frozen reviewed content, target, strategy and backup mode, even when the preference changes while manual execution races the UI. Only a newly reviewed bundle can adopt changed settings.

**Q81 C after proven closure:** Temporary files become cleanup-eligible only after every admitted attempt has been reconciled, device-side admission is closed and qualified originals/results are safely retained. **Deletion failure after verified closure is a warning** with persistent `cleanup_pending` and retry; it does not block otherwise reconciled setup or later valid steps, because a retained script is inert. **Unverified closure** remains a blocking authority problem, never a cleanup-only warning.

**T13b integration acceptance:** start racing admission closure; successful run, proven closure, failed cleanup, released barrier and manual launch of retained script with **no mutation**; backup preference invalidation racing actual start; restart or replacement bundle unable to reactivate old authority; cleanup failure remaining nonblocking after closure. Retain reversed ZIP arrival, completed-first/interrupted-second results, attempted concurrent launch, immutable per-invocation evidence, waived/declined file backups, exact staged content and strict Recipe dependencies.

- Each ZIP is a run/attempt-bound report with reviewed-plan digest, stage/device identity, operation IDs, outcomes and hashes, bounded sanitized logs and failures. Strict ZIP entry/path/decompression/count/schema/hash validation is mandatory. Archive import to protected host report storage is separate from independent postcondition verification; a claimed `success` does not establish protected file correctness or emulator usability. Duplicate archive arrivals never overwrite earlier attempts.
- **Device cleanup:** Separate **Recovery Originals** (retained while recovery is required) from temporary **Privileged Setup Bundle**, ZIP and scratch files. Only **no-longer-needed, verified-owned** artifacts become **cleanup-eligible** after results/recovery retention and invocation reconciliation. EmuChef automatically attempts deletion and verifies its outcome. **Only after proven admission closure and complete attempt reconciliation**, failed cleanup is **Q81 C: nonblocking warning** plus persistent `cleanup_pending` obligation with retry at the next authorized reconnection and precise manual guidance if never reconnected; it must not by itself fail reconciled work or valid later operations. Transport, identity or execution-authority loss still follows existing fail-stop/session rules. Retain originals until their independent approved retention policy expires.
- **First OEM acceptance proof (Q79 A):** a reviewed root script copies the main RetroArch `retroarch.cfg` to its App Definition `external_app_data/files/retroarch.cfg`, with original-state checks, backup/waiver where required and verified content. This is **only** the protected config-copy proof—not a claim of full typed parity, resource provisioning or app usability.

## 5. Product support and evidence gates

Initial target: Apple Silicon native macOS EmuChef proper, one device; AYN/Retroid/AYANEO OEM runner availability through Device Profiles; first selected RetroArch AArch64 app build with exact version/digest; candidate Pocket Air Mini / `GT78-VN` Android 11/API 30 non-root. That Profile currently sets `app_data_write: false`, and the current App Target resolver gates both `app_data` and `external_app_data` on it. Existing planner tests permit pruned required RetroArch steps, including final launch. **Registration is not physical support qualification**. T06a must prove a supported path for config, required resources and a complete unpruned milestone operation graph; T06b separately validates actual emulator use; T13b/T15 require actual T18/T19 strategy evidence when OEM is needed. No flag flip, unproven root, implied broad model support or silent omission.
 
- **G0:** authoritative docs, tracking cutover, copy semantics and scoped qualification obligation inventory.
- **G1:** one-setting/one-writer/one-destination confirmed-absent no-clobber UI → Rust plan → immutable review → qualified gated creation → verified-or-unverified outcome.
- **G2:** complete RetroArch new/already-installed and running-app setup including internal/SD content, configuration, stage reviews and required graph. Where OEM is required, integrated T18/T19 and first protected `retroarch.cfg` copy proof, plus supported destination/config/ROM/BIOS and app-side usability evidence. Do not claim every brand/model or full parity from one physical case.
- **G3:** complete second emulator with genuinely different configuration format using the same trusted setting/composition system.
- **G4:** library-origin generated config via common T09 composition/review/qualified deployment, exact release-scoped evidence, signing/notarization/clean-Mac trust and **separate** production release approval. Never automatically enable real execution after an issue closes.

**Qualification evidence is target/build/adapter/workflow-specific.** Existing physical/manual Phase 6D.6 gaps remain owner-deferred (not waived) and block applicable capabilities/release gates until passing evidence or contract-grounded inapplicability under an expressly approved release scope. Existing Phase 6B/5H accessibility, Phase 6E/6F recipes/target matrices, Phase 6G release trust and signing obligations remain tracked in [qualification-obligations.md](qualification-obligations.md); old evidence must not be silently promoted to a new implementation. Device operations, firmware/host permission changes and publication remain separately authorized.
